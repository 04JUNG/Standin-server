# 12초 체형 판독 예산 실측 — 2026-10-17

**현재 직렬 판독 + 재검토 구조로는 승인된 추천 품질을 12초 안에 유지하지 못했다.** 코드·환경변수·배포를 변경하지 않고 최종 구현의 시간 예산만 120초 → 12초로 바꾸어 측정했다.

## 평가 기준 고정

사용자가 현재 28명 보고서에 대해 “이거 정답으로 쓸 수 있겠고 12초 안에도 가능해?”라고 확인했다. 보고서의 최종 추천 계열·프리셋 ID 28개를 `COARSE_APPROVED_REFERENCE.json`에 사용자 승인 개발 평가 기준으로 고정했다. 원본·crop·보고서·결과 파일 해시를 기록했다. 이는 생성 결과를 사용자가 승인한 기준이며 독립/블라인드 정답 세트가 아니다. 기존 작가 설정 직접 확인 2건은 `COARSE_CONFIRMED_LABELS.json`에 별도로 유지한다. 정답은 모델 요청에 보내지 않는다.

## 방법

동일한 28명 crop, 최초 `gemini-flash-lite-latest`, 재검토 `gemini-3.8-flash`, `timeout_seconds=12`. 기존 평가기와 같이 4명씩 7배치, 동시 작업 2개, 반복 1회다. 측정 범위는 체형 client의 최초 호출부터 재검토/복구 반환까지이며, pose 파이프라인·BFF·UI 시간은 포함하지 않는다. 따라서 앱 전체의 12초 SLA 검증이 아니다. 요청 타이밍을 실제 SDK 호출 앞뒤에서 측정했다.

| 항목 | 결과 |
|---|---:|
| 남녀 주 추천 일치 | 26/28 (92.9%) |
| 실제 시각 판독 계열 일치 | 24/28 (85.7%) |
| 정확한 프리셋 ID 일치 | 23/28 (82.1%) |

| 엄밀히 12초 초과한 배치 | 3/7 (12.008~12.071초) |

최초 호출은 3.648~5.578초였다. 재검토는 남은 약 6.4~8.0초를 사용하고 모두 ReadTimeout으로 복구했다. 12초 timeout 설정이 직렬 호출과 직렬화·후처리를 포함한 엄밀한 12초 반환 상한을 보장하지도 않았다. 전체 28명 평가 wall time 약 32.9초는 동시 실행한 평가기의 시간이며, 컷 한 장 지연과 같지 않다.

`124702:p0`는 중성형 최초 판독 뒤 재검토가 실패하여 **남성 BASE**로 돌아갔다. `131040:p1`도 최초 잠정 여성 판독이 남아 여성 BASE로 어긋났다. `124637:p0`는 남성 BASE를 유지했다.

프리셋까지 어긋난 5건은 `124702:p0`, `131040:p1`, `131056:p0`(IDEAL83→BASE), `131127:p0`(BASE→MUSCULAR), `131224:p0`(SLIM→BASE)다. 뒤의 세부 프리셋 변동은 최초 모델 출력 변동도 포함한다. 시간 제한 때문에 발생한 변화라고 모두 단정하지 않는다. 설정 기본값이 우연히 정답과 같았던 경우를 실제 판독 성공으로 세지 않았다.

## 다음 성능 개선의 기준

12초 내 반환뿐 아니라 **124702 여성 BASE 유지와 승인된 28명 추천 품질**을 함께 검증해야 한다. 우선 의상 근거 판독과 계열 결정을 단일 호출로 합치거나, 추론·응답 길이를 줄이는 별도 후보를 평가할 수 있다. 이는 아직 구현·검증된 12초 해법이 아니다. 외부 API의 지연 변동이 있으므로 여러 번의 실행과 실제 컷별 인원수로 검증해야 한다. 이미지별 정답 캐시를 속도 개선으로 사용하지 않는다.

원격 원문·28개 개별 결과·타이밍·재현 스크립트는 `artifacts/body-matching/2026-10-17-budget12/`의 `run/results.json`, `SCORES.json`, `timings.json`, `benchmark.py`에 보존했다. 이 작업은 평가·문서만 추가했으며 런타임 코드·실제 .env·배포·머지를 변경하지 않았다.
