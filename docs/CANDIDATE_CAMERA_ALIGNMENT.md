# 후보 미리보기 방향 일치

2026-10-07. 구현 버전 `candidate-camera-v1`.

## 문제와 기준

검색은 원본 BVH에 0/45/90/180°를 적용한 투영을 비교했다. 기존 썸네일은
어깨·골반 카메라, 신규 큐레이션 썸네일은 고정 월드 카메라를 사용했다.
검색의 `front`는 해부학적 정면과 다르고, 신규 45° 카메라의 부호도 검색 투영과 달랐다.
따라서 검색 view를 썸네일 이름으로 사용하는 것으로 러프 방향을 재현할 수 없다.

정면은 COCO-17의 **좌골반→우골반 구분과 골반 중심→양어깨 중심**으로 만든
전방 벡터로 정한다. Y-up 수평 yaw만 정규화한다. 몸을 세우는 전체 축 정렬은 하지
않는다. 옆으로 눕거나 거꾸로 내려찍는 포즈의 기울기를 보존한다.
전방이 수직에 가까운 경우에는 yaw를 억지로 정하지 않고 camera=null로 남긴다.

## 경로

1. `/analyze`는 기존 검색 결과를 유지하면서 각 후보에 선택적 `camera`를 추가한다.
2. 마스킹된 실관측 관절 5~16번만으로 양수 scale/translation 및 yaw/pitch/roll을
   fitting한다. 어깨 양쪽과 총 4개 이상이 필요하다. BVH Head를 눈·코 좌표로 쓰지 않는다.
3. **인물에 귀속된** VLM view만 표시 각도 범위를 제한한다. 컷 전체 view는 다인 간
   소유권이 불확실하므로 사용하지 않는다. 정면은 ±30°, 측면은 ±90° 주변,
   후면은 180° 주변이다. 잘 맞지 않으면 `canonical_fallback`으로 명시한다.
4. BFF는 카메라를 Job 결과에 보관한다. 후보 ID/view는 검색 식별자 그대로다.
   표시 태그만 camera.display_view를 사용한다. URL에 클라이언트 회전값을 받지 않는다.
5. 새 `/v1/pose-candidates/:id/aligned`는 선택 이전에도 해당 Job 소유자에게만
   전체 포즈 preview를 제공한다. 원본 SHA가 달라지거나 격리된 포즈는 409다.
6. Converter `/convert-framed`는 동결 retarget 이후 FBX 전체에 proper rotation을
   한 번 적용하고, **완성 FBX를 다시 불러와 고정 정면 카메라**로 미리보기를 만든다.
   부분 범위도 같은 회전을 사용한다. 기존 해부학적 썸네일을 재사용하지 않는다.
7. Refine은 정해진 카메라 좌표에서 기존 안전 게이트로 실행한 뒤 루트 회전을
   역변환한다. BVH 다운로드는 원래 방향이다. FBX 및 최종 preview에만 카메라를 적용한다.

카메라는 원본 BVH SHA에 귀속된다. matrix는 3×3 Y-up 모델 회전이며
전치행렬이 역변환이다. 스케일·반사·비유한 수를 거절한다. world yaw 부호가 있는
별도 Euler 해석을 BFF/클라이언트에 구현하지 않는다.

## 배포와 호환

Converter(카메라 지원) → BFF(전달·다운로드) → 클라이언트(개별 이미지 로딩) →
Inference(카메라 생성) 순서로 배포한다. 새 클라이언트를 제공한 뒤 카메라 생성을
활성화해야 기존 클라이언트의 전체 분석 대기에 렌더 시간이 합산되지 않는다.
기존 작업에는 camera가 없으므로 기존 경로가 유지된다. 개선된 각도를 보려면 새로
분석해야 한다. 구 converter가 회전값을 무시하면 BFF/Inference는 integrity 오류로
거절하며 잘못된 각도의 그림을 성공으로 표시하지 않는다.

새 그림은 Blender로 생성하므로 정적 썸네일보다 첫 요청이 느리다. BFF는 Job/인물/
후보/모델/회전별로 10분, 총 128 MiB 한도 캐시를 사용한다. 후보 동시 요청은 16개까지
병합·처리하며 요청 제한은 300초다. 같은 원본·범위·모델·각도의 후보 preview와 최종 FBX는
캐시에서 같은 산출물을 재사용한다. 클라이언트는 후보 목록을 먼저 열고 각 이미지를
개별 Query로 받아 로딩/재시도를 표시한다. 전체 분석의 3분 제한에 렌더 대기를 합산하지 않는다.
로컬 5개 콜드 요청은 총 173초였으므로 지연이 해소됐다고 주장하지 않는다. 스테이징 다중 사용자
지연 측정과 라이브러리별 사전 변환 캐시는 후속 최적화 대상이다. 카메라 요청의 Blender 작업
제한은 CONVERTER_CAMERA_TIMEOUT_SECONDS(기본 60초), 기존 변환은 원래 제한을 유지한다.

## 검증

- `tests/test_candidate_camera.py`: 소스 yaw가 달라도 같은 정면으로 수렴, 앞/뒤 제약,
  양수 scale, 얼굴 proxy 제외, 역전 포즈 유지, 모든 Euler 순서의 루트 왕복.
- `tests/converter/test_framing_contract.py`: 회전값 전달/회신, 잘못된 행렬·반사 거절,
  converter가 회전을 무시하는 경우 실패.
- `tests/converter/verify_camera_runtime.py`: 실제 Blender에서 전신·반신·흉상·두상 FBX를
  내보내고 재임포트하여 관절 좌표가 동일한 rigid transform인지 비교.
- BFF: 소유권/캐시 재접근/원본 변경/격리/클라이언트 회전값 무시/기존 ID 유지.
- `scripts/audit_pose_camera.py --bvh-dir ... --output ...`: 원본을 수정하지 않는 방향 감사.

로컬 스테이징 번들 1,708개에서 기준 계산 가능 1,693개, 모호 15개였다.
가능한 포즈 중 643개는 원본 정면과 해부학적 정면 차이가 30°를 넘었다.
첨부 화면의 CMU 2개와 100style HighKnees 1개를 동일한 정면 기준으로 실제 렌더했다.
원본 러프는 이번 메시지에 없으므로 재현 입력은 해당 BVH의 알려진 정면 투영이다.
실제 러프에 대한 관절 검출 오차, 원근, VLM 앞/뒤 오판까지 해결됐다는 뜻은 아니다.
단일 2D 입력의 깊이 모호성은 계속 `depth_ambiguous=true`로 표시한다.
