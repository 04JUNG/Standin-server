# 검색·리파인·최종 FBX 평가 하네스 보완 설계

작성일: 2026-10-27 · 상태: **검토용 설계, 미구현**

최신 원격 develop과 별도 리파인 v3 PR을 읽어 작성했다. 이번 작업은 문서·준비 양식 작성이며, 모델 호출·러프 재분석·앱 E2E·운영 설정 변경·배포는 하지 않았다. 아래의 새 명령·모듈·지표는 명시한 경우를 제외하면 구현 제안이다.

## 1. 결정 요약

기존 `standin_eval/`의 데이터셋 봉인, HTTP 실행, 고정 입력 재생, 인물 대응, 블라인드 평가, 결과 비교를 재사용한다. 여기에 **현재 기준 버전과 v3의 비교**, **선택 체형·손이 반영된 실제 최종 FBX 검증**, **앱의 실제 저장까지 연결하는 실행 기록**을 추가한다.

최종적으로 답할 질문은 다음 세 가지다.

1. 같은 러프에서 작가가 쓸 만한 후보를 더 자주 찾는가?
2. 선택한 포즈를 보정하면 의도에 더 가까워지고, 수정 시간이 줄며, 뒤틀림·관통이 늘지 않는가?
3. 선택·검수한 체형·손·포즈·인물 배치가 사용자가 받은 FBX에도 보존되는가?

평가 결과는 **품질 개선, 안전성, 파일 무결성, 시간, 검증 범위**를 각각 표시한다. 파일을 열 수 있다는 사실만으로 자세가 좋다고 판정하거나, 관절 좌표가 비슷하다는 사실만으로 실제 메시가 안전하다고 판정하지 않는다.

### 도원이 먼저 준비할 것

| 준비물 | 첫 준비 범위 제안 | 적는 내용 |
|---|---|---|
| 대표 러프 | 실제 작업의 연속 컷 또는 사전 무작위 표본 20장 | 원본 PNG, 작품/페이지 묶음, 인물 수, 3D 보조가 필요한 인물과 동작 의도 |
| 어려운 러프 | 별도 10장 | 가림, 단축, 뒤/옆모습, 접촉·지지, 여러 인물이 섞인 실패 사례 |
| 최종 검증용 러프 | 위 자료와 작품/장면 묶음이 겹치지 않는 추가 20~30장부터 확보 | 튜닝 담당자에게 결과를 공개하지 않고 보관. 최종 필요 표본 수는 첫 평가 후 산정 |
| 체형·손 예시 | 지원할 기본 체형 5종의 정확한 ID/버전과 대표 커스텀 조합 | 기본값·자주 쓰는 값·허용 범위 끝값, 좌우 손 프리셋, 주로 쓰는 출력 범위 |
| 사람 평가자 | 실제 웹툰 작업자 최소 2명부터 | 바로 사용 가능 여부, 수정 내용과 시간, 눈에 보이는 결함, 기존/신규 선호 |
| 사용하는 제작 도구 | 실제 사용하는 CSP/Modeler 등의 이름·버전·OS | 최종 FBX가 열리고 필요한 편집이 가능한지 확인할 환경 |

위 장수는 **평가 절차를 만드는 시작 분량**이다. 제품 성공률이나 출시 안전성을 입증하는 표본 수가 아니다. 가능한 한 여러 작가·작품을 확보하고, 같은 작품의 여러 컷을 독립 사용자 표본처럼 세지 않는다. 사용자는 러프·의도·판단을 준비하고, 해시 생성·관절 좌표 라벨링·파일 생성·무작위 평가 ID 부여는 구현 담당자가 맡는다.

빈 양식은 [러프 접수](evaluation-harness-20261027/rough-intake.csv), [인물별 의도](evaluation-harness-20261027/person-intent.csv), [검색 평가](evaluation-harness-20261027/search-review.csv), [리파인 비교](evaluation-harness-20261027/refine-review.csv), [최종 FBX 평가](evaluation-harness-20261027/fbx-review.csv)에 있다. 작성 순서와 각 칸의 의미는 [양식 안내](evaluation-harness-20261027/README.md)를 따른다.

## 3. 평가를 세 층으로 실행

```text
① 검색: 동일 러프 / 동일 관측 → 기준 검색과 새 검색 → Top-5 비교
② 리파인: 동일 관측 / 동일 선택 BVH·카메라 → 무보정·기준 F25·새 v3 비교
③ 제품 전체: 러프 → 검색 → 선택 → 체형·손 → 보정 → 최종 FBX → 실제 저장·재열기
```

검색만 바꾼 평가에서는 모델·라이브러리 등 나머지를 고정한다. 리파인만 비교할 때는 **같은 선택 포즈**를 사용한다. 서로 다른 검색 Top-1을 보정하고 차이를 전부 리파인 효과라고 해석하지 않는다.

제품 전체 평가는 실제 달라진 모든 단계의 총효과를 확인한다. 서로 다른 실행 결과를 섞어 이긴 단계만 조합한 가상 성공률을 만들지 않는다.

| 실행 종류 | 목적 | 시간 해석 |
|---|---|---|
| 고정 입력 replay | 같은 VLM·포즈 관측에서 코드 변경의 효과 분리 | 제품 전체 지연으로 사용하지 않음 |
| 실제 provider HTTP | 라우팅·가림 판독·검색 및 모델 호출 변동 확인 | 실제 요청·재시도·실패·queue를 포함 |
| Converter/Blender 검증 | 체형·손·출력 범위·FBX 전달·메시 안전 | 독립된 변환·검증 시간과 자원 측정 |
| 설치 앱 검증 | 전체화면/플로팅바, 네이티브 저장·취소·재사용 | 사용자가 겪는 시간과 최종 파일 확인 |

실험 v3의 off/shadow는 기존 F25 출력 보존을 검증하는 모드다. shadow 계산이 됐다는 사실을 v3 결과가 사용자 파일에 적용된 것으로 집계하지 않는다. 장면의 `auto-correct-v4` 저장 모드와 리파인 v3 알고리즘 버전도 별개 필드로 기록한다.

## 4. 데이터셋과 준비할 러프

### 4.1 세트 분리

| 세트 | 용도 | 운영 원칙 |
|---|---|---|
| D0 회귀·합성 | 파서·좌표계·결정성·안전 실패·복구 검증 | selected12, 기존 실패 사례, 정답을 아는 3D 합성 입력 재사용 |
| D1 튜닝 | 라벨 기준, 허용 오차, 지연 예산, 개선 방향 결정 | 대표셋과 어려운 사례를 구분. 결과를 보고 수정 가능 |
| D2 봉인 검증 | 고정된 출시 후보 최종 비교 | 작가/작품/원본 장면 묶음으로 D1과 분리. 결과 공개 후 같은 셋에 재튜닝하면 새 holdout 필요 |
| D3 사용 관찰 | 실제로 도움이 되는지 확인 | 소수 사용자의 실제 작업·수정·저장·재사용 관찰. 대시보드와 연계 |

실제 분포를 볼 대표셋에는 인물 없음·얼굴만 있는 컷 등도 수집 그대로 남긴다. 제품 타깃 인물인지 **결과를 보기 전에** 표시하고, 라우팅 제외의 정확성은 별도로 평가한다. 어려운 사례를 많이 모은 셋의 성공률을 전체 사용자 성공률로 발표하지 않는다.

### 4.2 러프 구성 체크리스트

- 기본: 전신·반신·상체, 서기·앉기·쪼그리기·달리기, 정면·측면·후면.
- 카메라: 45도 부근, 위/아래 시점, 강한 단축, 좌우 반전 혼동.
- 가림: 손만 안 보임, 팔꿈치가 가림, 하체 없음, 다른 인물/소품에 가림, 인물 경계가 겹침.
- 관계: 손을 허리/무릎에 댐, 양손 맞닿음, 바닥/의자 지지, 공중 자세, 다인 상호작용.
- 결과 공백: 기존 후보 0개, 후보는 있지만 의도가 다름, 비슷한 후보만 반복, 생성 fallback이 필요한 사례.
- 제품 회귀: 종이인형 썸네일·잘못된 방향, 손 변경 후 구버전 파일, 미리보기 실패 중 저장, 다인 배치/크기 왜곡 등 이미 발견한 사례.

태그는 중복될 수 있다. 숨은 관절의 정답을 억지로 적지 않으며 `보임 / 가림 / 화면 밖 / 판단 불가`를 구분한다. 가려진 실제 자세를 작가가 알고 있다면 **작가가 별도로 제공한 의도**로 보관하고, 이미지에서 직접 관측한 좌표와 섞지 않는다.

### 4.3 러프와 함께 적을 최소 정보

1. 컷 ID·원본 파일·작가/작품/페이지 묶음 ID. 실명 대신 내부 별칭 가능.
2. 인물 수와 인물별 위치 표시. 자동 bbox 초안은 사람이 확정하고 영구 `person_id`를 부여.
3. 각 인물의 핵심 동작·보존해야 할 부위·좌우·보이는 방향·접촉/지지 의도.
4. 가림 여부, 3D 보조를 쓰려는 대상인지, 판단 불가 여부.
5. 평가/내부 공유/외부 VLM 전송 가능 여부. 불명확한 자료는 실제 provider 실행에서 제외.
6. 희망 체형·손·출력 범위와 실제 쓰는 제작 도구.

동의된 서비스 기록·커스텀 체형을 평가셋에 넣을 때도 목적과 사용 가능 범위를 먼저 확인한다. 평가를 위해 모든 사용자 원본을 자동 수집하는 기능은 이 설계에 포함하지 않는다.

## 5. 공통 실행·증거 계약

각 실행은 코드 커밋뿐 아니라 아래 자료를 고정한다. 재현에 필요한 비공개 파일은 별도 권한 저장소에 보관하고 공개 report에는 해시·식별자만 넣는다.

| 묶음 | 필수 바인딩 |
|---|---|
| 입력 | dataset/GT/rubric 버전·해시, 컷·영구 인물 ID, split/group, 이미지 해시 |
| 관측 | VLM provider/실제 응답 모델·prompt/schema 해시, 포즈 모델·decoder·보정 설정, 관절별 출처/가시성/귀속 근거 |
| 검색 | DB·BVH·태그·카메라/index 버전, pose/family/candidate ID, rank, mirror·projection·후보 종류·제공 여부 |
| 선택 | 선택한 원본 BVH 해시, person/selection revision, 카메라·출력 범위, 저장 모드 |
| 체형·손 | character/asset/shape/controller/rig/bone-map 버전·해시, 수치, 좌우 프리셋·손 라이브러리 해시 |
| 실행 | 기준/후보 arm 정의, feature flags, Converter/Blender build, 장비·동시성·cache 상태, seed·deadline·허용 오차 |
| 출력 | 원본/보정 BVH, 인물별 최종 FBX, scene FBX, 검수 receipt, 미리보기, 다운로드·실제 저장 바이트 해시/크기 |
| 검사·사람 평가 | 검사기 버전·정책·적용 범위·완료 여부, 안정된 결함 ID, 라벨·라벨러·assignment·소요 시간 |

`cut → gt_person → candidate → selection_revision → body/hand_revision → artifact → saved_file`의 연결을 유지한다. `personIndex`는 요청 안의 순번으로만 쓰고 영구 인물 ID 대신 사용하지 않는다.

새 arm registry는 baseline을 명시적으로 지정하며 과거 `B0_no_refine/B1_v1/B2_v24_aggressive` 기록을 그대로 읽을 수 있어야 한다. 비교 계약을 바꾸면 새 schema/evaluator 버전을 발급한다. 현재 F25를 과거 B2 이름으로 바꾸어 기록하지 않는다.

추가 기록 제안: `selections.jsonl`, `exports.jsonl`, `mesh_evidence.jsonl`, `native_saves.jsonl`, `review_sessions.jsonl`. 기존 결과 파일을 유지하고 새 버전의 reporter가 연결한다. 오류·기권·timeout도 해당 평가 단위의 행을 남긴다.

기존 requested/actual backend 검사를 유지한다. Gemini·실제 포즈 모델을 요청했는데 mock으로 대체되거나 library/model manifest가 다르면 해당 실행을 무효 처리한다. 호환되지 않는 두 실행을 비교할 때는 변경된 요인을 명시하고, 단일 알고리즘의 효과로 해석하지 않는다.

## 6. 검색 평가

### 핵심 지표

| 지표 | 정의·분모 |
|---|---|
| Top-5 활용 가능률 | 사전에 정한 타깃 인물 중 Top-5에 활용 가능한 후보가 한 개 이상 있는 비율. `바로 사용`과 `참고 후 수정`은 따로 표시 |
| Top-1 활용 가능률 | 같은 고정 인물 분모에서 첫 후보의 활용 가능 여부 |
| 예산 내 후보 제공률 | 실제로 표시 가능한 후보·활용성 라벨·응답 시간 조건을 함께 만족한 인물 비율 |
| 컷 전체 성공률 | 컷에서 필요하다고 지정한 모든 인물에게 후보가 제공된 비율. 인물 단위 수치와 분리 |
| 의도·방향·다양성 | 동작/좌우/방향의 위반, 중복 family 비율, 필요한 자세 구조 포함 여부 |
| 검색 무결과·인식 실패 | 인물 누락·귀속 오류·가용 관절 부족·후보 0개·제공 정책 차단을 구분 |

기존 `candidate_coverage_at_5`, `accepted_at_1`, `assist_success_at_5`, 실패 funnel을 재사용하되 **정적 썸네일의 활용성 평가를 실제 FBX 안전 통과로 해석하지 않는다**. 기존 지표의 뜻을 조용히 바꾸지 않고 새 지표/버전을 추가한다.

Top-5 전체를 refine·메시 검증하려면 별도의 오프라인 평가 비용이 필요하다. 선택한 1개만 최종 검증했다면 결과도 `선택 후보의 최종 검증`으로 제한한다.

### 실패 원인 진단

- 인물 누락/다른 인물 관절 혼입은 인식·귀속 단계의 증거로 판정한다.
- 라이브러리 안의 검수된 적합 후보를 확인했는데 순위에서 빠졌으면 검색 실패 근거가 된다.
- 적합 후보를 찾지 못했다는 이유만으로 라이브러리에 없다고 단정하지 않는다. 불충분하면 `search_or_library_unresolved`를 유지한다.
- 검색 후보·유사 대안·새로 생성한 포즈의 출처와 각각의 실패를 보존한다. 생성 활성/비활성, 실행 안 됨, 생성 실패, 검수 거절을 구분한다.
- 검색된 카메라/반전과 정적 썸네일 asset을 대조한다. 화면에 보인 방향·이후 적용된 방향의 불일치를 별도 결함으로 남긴다.

### 문장 검색 확장

문장 검색을 제공하는 빌드도 별도 입력군으로 평가한다. 실제 사용자 문장과 기대 동작·좌우·방향·부정 조건·소품/관계를 사전에 적고, 같은 Top-5 블라인드 활용성 지표와 무결과·지연을 사용한다. 예를 들어 ‘오른손을 머리 위로 든 자세’에서 좌우/정도 위반을 구분한다.

러프 검색과 문장 검색은 입력·정답·분모를 나누며, 문장 검색의 API/라이브러리 계약 adapter는 별도 구현한다. 러프 관절 근거가 없는 문장 후보를 자동으로 러프 리파인 평가에 넣지 않는다. 생성 fallback은 실행 조건·실패·검수·출처를 보존하는 별도 arm으로 비교한다.

## 7. 리파인 평가

### 7.1 같은 선택 포즈에서 비교

기본 비교는 `무보정 선택 B0 / 고정한 기준 F25 / 후보 v3`다. 선택 BVH·관측·체형·손·카메라·출력 범위·예산을 고정한다. 과거 v1 비교는 진단용 선택 arm으로 남긴다.

독립 평가기는 solver 내부 loss나 `accepted=true`를 성공 정답으로 사용하지 않는다. 반환된 BVH를 다시 파싱해 공통 좌표·카메라로 측정하고, 최종 메시도 별도로 검사한다. 공유 FK/충돌 유틸리티의 버그를 양쪽이 함께 통과하지 않도록 알려진 정답의 합성/음성 fixture와 독립 계산을 추가한다.

### 7.2 측정 항목

| 평가 | 내용 |
|---|---|
| 러프 유사성 | 관측 가능한 관절·사지 방향·endpoint의 투영 오차, 작가의 의도 일치 판단 |
| 뒤틀림·관통 | 정확한 target rig의 관절 제한, 실제 변형 메시의 교차·접힘·퇴화, 신규/악화 및 원래 결함 |
| 보존 | 사용자가 고른 자세의 핵심, 움직이면 안 되는 부위, root·출력 범위·비활성 채널 |
| 접촉·지지 | 확인된 손–몸/손–손/지지발 관계. 접촉 면·간격·법선 등 해당 profile이 지원하는 검사 |
| 복구 | 거절·timeout·지원 불가에서 약속한 기준 BVH/기존 artifact로 정확히 복구했는지 |
| 활용성 | 블라인드 win/tie/loss, 바로 사용/수정 후 사용/사용 어려움, 실제 수정 시간 |

실러프에는 3D 정답이 없으므로 MPJPE를 만들지 않는다. 알려진 3D 합성 입력의 오차는 진단 전용으로 분리한다. 기존의 capsule/스틱피겨 충돌 검사는 proxy로 표시하고 실제 메시 안전을 대체하지 않는다.

### 7.3 가림 전용 평가

- 관절별 `직접 관측 / 모델 추정 / 가림 / 화면 밖 / 귀속 불확실`과 근거를 보존한다. VLM의 보임·좌우 주장을 독립 인증으로 승격하지 않는다.
- 직접 확인 가능한 부위가 좋아졌는지, 가린 부위를 근거 없이 이동시키거나 다른 인물 관절을 따라갔는지 따로 검사한다.
- 가린 팔꿈치의 endpoint solve, 골반 없는 upper-only 등 미지원 상태는 명시적 기권으로 기록한다. 기권을 품질 개선으로 세지 않는다.
- 기존 repair 경로가 제안한 추정 좌표는 provenance를 분리한다. 이번 하네스 설계가 VLM에게 새 정답 좌표 생성을 지시하거나 현재 보정 권한을 완화하지 않는다.
- 정보가 부족해서 안전하게 그대로 둔 경우와, 실제로 개선된 경우를 각각 집계한다. 전체 타깃 분모와 v3 적용 가능 부분집합을 함께 보고한다.

## 8. 최종 FBX 평가

### 8.1 변환·재열기·안전·활용성을 각각 검증

| 층 | 필수 확인 |
|---|---|
| 전달 무결성 | artifact/review revision, 서버 응답 SHA/크기, 다운로드 바이트, 실제 저장 바이트의 일치 |
| 구조 | 재import 성공, 예상 골격·메시 수, 본 계층·스킨 바인딩·유한값, 지원 출력 범위의 구조 |
| 변형 보존 | 기준 snapshot과 재import 후 월드 좌표의 본·변형 정점 비교. 인원/체형/손 적용 결과도 확인 |
| 실제 메시 안전 | 전신 또는 인증된 해당 출력 범위의 교차·접힘·퇴화·관절·필요한 접촉/지지 검사. 검사 생략·시간 초과는 unknown |
| 장면 | 포함/제외 인물, 중복·비연속 인물 ID, XYZ/yaw/scale, 단위·축·mirror·camera의 보존 |
| 사용자 도구 | 대상 CSP/Modeler 등에서 실제 열기, 상대 크기·방향·손·범위·활용 가능 여부 |

인물별 안전 검사를 통과해도 다인 합성 후 서로 관통할 수 있다. 인물 간·소품 접촉은 별도의 scene 검사와 정답 근거가 필요하며, 미구현이면 `scene_interaction_unverified`로 표시한다. 현재 합성 API의 배치 보존 검사를 상호작용 안전 보장으로 표현하지 않는다.

### 8.2 꼭 포함할 매트릭스

- 카탈로그의 지원 체형 5종을 ID/해시로 고정. 조절 가능 여부에 맞춰 기본값·대표 커스텀·허용 끝값을 검사한다. 임의의 모든 수치 조합을 인증했다고 주장하지 않는다.
- 좌우 다른 손·한쪽 변경·기본 손 복구, 손목과 팔의 연결. 손 프리셋 메타데이터뿐 아니라 실제 본/메시가 달라졌는지 확인한다.
- `full / half / bust / shoulder_head / head`의 지원 범위. 특정 full-body snapshot의 증거를 잘린 범위에 자동 승계하지 않는다.
- 단일 인물과 다인 2/3/8명, 같은 포즈 반복, 다른 크기·회전·상대 위치, 일부 제외, 잘못된 0명/9명 거부.
- 장면 `original-selection`과 지원되는 `auto-correct-v4`를 분리. 자동 보정에서 포즈·범위가 바뀌었다면 검수 summary와 실제 파일의 차이를 대조한다.
- 정방형·세로·가로 러프의 동일 FBX 재렌더. 카메라 fit/단위 변환 오류로 미리보기만 커지거나 잘리는 회귀를 검사한다.

전체 조합의 곱을 매번 실행하지 않는다. 빠른 회귀는 고정된 대표·음성 사례와 pairwise 조합, 야간/출시 후보는 지원 범위별 실제 Blender 검사, 실제 제작 도구 확인은 선별된 핵심 조합을 실행한다. 검사하지 않은 조합은 coverage 표에 남긴다.

### 8.3 설정 변경·미리보기·저장 경쟁 상태

| 시나리오 | 기대 결과 |
|---|---|
| FBX 준비·검증 완료, 미리보기 대기/실패 | 현재 계약이 허용하는 저장이 가능하고, 미리보기 성공과 파일 준비 성공은 별도 기록 |
| 준비 중/검수 후 손·체형·포즈·범위·인물 포함 변경 | 이전 revision을 현재 결과로 저장하지 않음. 재준비 또는 명시적 stale 오류 |
| 파일 저장 후 손 변경 | 이미 저장한 파일은 유지. 다음 저장은 새 revision·새 artifact로 구분 |
| 작업 변경·삭제·다른 설치 접근·만료 receipt | 이전/타인 artifact를 반환하지 않음 |
| 요청 취소·timeout | 앱 취소와 서버 연산 중단을 구분. 서버가 계속 처리할 수 있는 계약을 성공 취소로 오해하지 않음 |
| 앱 저장창 취소·쓰기 실패·파일명 중복 | 성공 저장과 분리. 실제 저장 성공에만 saved-file 증거를 연결 |
| 느린 이전 응답이 나중에 도착 | 새 선택/손/체형 상태를 덮지 않음 |

Blender 재export는 metadata 등으로 바이트가 달라질 수 있다. 일반 재현은 의미·기하 허용 오차로 비교하고, **동일 artifact 전달·기존 파일 복구**를 약속한 경계에서만 정확한 바이트/해시 일치를 요구한다. BVH exact fallback과 새 설정으로 다시 만든 FBX의 해시를 혼동하지 않는다.

## 9. 사람 평가표

### 9.1 검색 후보: 인물별 Top-5

| 질문 | 답변 |
|---|---|
| 이 인물의 핵심 동작·방향·좌우가 맞는가? | 맞음 / 일부 다름 / 다름 / 판단 불가 + 부위·이유 |
| 후보를 작업에 쓸 수 있는가? | 바로 사용 / 참고 후 수정 / 사용 어려움 / 판단 불가 |
| 무엇을 고치겠는가? | 포즈 구조 / 방향 / 체형 / 손 / 접촉 / 기타 |
| Top-5에서 고를 수 있는 후보가 있는가? | 있음(선택한 무작위 후보 ID) / 없음 / 미평가 |

후보별로 버전·원래 순위를 숨긴 union을 평가한 뒤 원래 Top-5 지표로 되돌린다. 별도로 실제 순위 화면에서 찾는 시간·선택 동작을 측정하는 사용자 과제를 둔다. 후보 순위를 숨긴 평가로 UI 탐색 시간을 추정하지 않는다.

### 9.2 리파인: 동일 포즈의 전후 비교

| 질문 | 답변 |
|---|---|
| 러프에 더 가까운 것은? | 왼쪽 / 오른쪽 / 같음 / 판단 불가 |
| 핵심 자세가 유지되는가? | 유지 / 조금 손상 / 심하게 손상 / 판단 불가 |
| 뒤틀림·관통·부유·접촉 문제가 있는가? | 없음 / 의심 / 확인 + 부위·심각도 |
| 작업에 쓸 수 있는가? | 각 결과에 바로 사용 / 참고 후 수정 / 사용 어려움 |
| 실제로 고치는 데 얼마나 걸렸는가? | 수정 시작/완료 시각, 완료 여부, 막힌 이유 |

원본 러프와 같은 비교 카메라를 사용하고 보조 정면/측면을 제공한다. 평가자가 버전마다 카메라를 따로 맞춰서 자세 오차를 숨기지 않게 한다. 좌우 배치는 무작위화하고 대응표는 비공개로 둔다.

수정 시간은 사람이 정한 실제 과제의 완료 시간이다. 한 사람이 같은 러프를 반복해서 익힌 효과를 줄이도록 순서를 교차 배정하거나 서로 다른 평가자에게 배정한다. 시간 제한에 걸린 미완료를 짧은 수정 시간으로 평균 내지 않고 완료율·제한 초과와 함께 보고한다. 직접 그리기 대비 시간 절약은 별도 직접 작업 baseline이 있을 때만 주장한다.

### 9.3 최종 FBX: 저장 파일을 실제 도구에서 열기

| 질문 | 답변 |
|---|---|
| 파일이 열리는가? | 성공 / 실패 + 도구·OS·버전 |
| 선택한 인물·체형·손·범위인가? | 일치 / 불일치 / 판단 불가 + 항목 |
| 방향·크기·배치와 보이는 최종 결과가 검수 내용과 맞는가? | 일치 / 불일치 / 판단 불가 |
| 작업에 사용할 수 있는가? | 바로 사용 / 참고 후 수정 / 사용 어려움 |
| 결함은 어디에 있는가? | 부위·종류·심각도·스크린샷 ID |

평가자는 가능하면 실제 제작 작업자 2명 이상으로 시작한다. 기존 하네스의 이중 평가·숨은 반복 검증을 재사용하고, rubric 조정은 D1에서 끝낸다. 불일치 조정 전 원라벨을 보존한다. LLM 평가는 분류 보조로만 쓰고 작가 활용성·실제 메시 안전의 최종 승인자로 쓰지 않는다.

## 10. 지표·지연·판정

### 주요 지표의 분모

| 지표 | 고정 분모와 해석 |
|---|---|
| 검색 활용 가능률 | 사전 확정한 타깃 인물. 인식 실패·후보 0·timeout도 포함 |
| 리파인 개선 | 동일 base가 봉인된 평가 인물/후보 단위. 실제 변경·기권·복구를 모두 표시 |
| 최종 안전 활용 가능률 | 사전 정한 저장 과제 중 **실제 최종 파일 검증 + 작가 활용성 + 시간 예산**을 모두 충족한 과제 |
| 실제 저장 성공률 | 사전 저장 과제와 저장 요청 조건부 비율을 함께 표시. 생성 성공만으로 로컬 저장 성공 처리하지 않음 |
| 다인 컷 성공 | 필요한 모든 인물과 배치가 맞는 컷. 인물별 성공 평균과 분리 |
| 수정 시간 | 완료 과제의 중앙값/p90와 완료율·미완료/시간 제한을 병기 |

활용성/메시 라벨 누락은 unknown이다. `평가 완료` 결과에는 누락이 없어야 하며, 진행 중 report는 성공/실패/unknown 수와 커버리지를 함께 보여준다. 판정 불가를 0초·안전·성공으로 대체하지 않는다.

지연은 업로드 → 모델/인식 → 검색 → 선택 → F25/v3 → 체형·손 변환 → 메시 검증 → 장면 합성 → 파일 준비 → 다운로드/네이티브 저장으로 나눈다. 미리보기 준비 시간과 실제 저장 가능 시점을 각각 기록한다. 서로 겹친 병렬 단계의 시간을 단순 합해 전체 시간으로 보고하지 않는다.

cold/warm, cache hit/miss, 1인/다인, 전체화면/플로팅바, 성공/실패/timeout, 처리시간/queue를 구분한다. 실제 provider의 조건부 호출·재시도·실패까지 종류별로 집계하고 토큰·비용을 기록한다. 호출을 고정 2회라고 가정하지 않으며 실패 요청의 비용을 모르면 unknown으로 남긴다.

기존 CLI의 5초 기본값, 과거 예시 기준의 p95 2초, 리파인 설계의 다른 예산은 현재 제품 전체 SLO가 아니다. D1에서 실제 장비·제품 구간을 측정한 뒤 구간별/전체 budget·timeout·최대 동시성·비회귀 허용치를 한 정책 파일에 고정한다. 특정 로컬 메시 검사 시간을 전체 사용자 대기 시간으로 표현하지 않는다.

### 판정 규칙 제안

- `PASS`: 사전 봉인한 품질 개선 기준·비회귀·안전·시간·표본/coverage 조건을 모두 충족.
- `FAIL`: 신규 hard 결함, 선택/파일 불일치, 소유권 오류, 잘못된 복구, 정해진 품질/지연 조건 위반.
- `INCONCLUSIVE`: 라벨·profile·검사 완료 증거·독립 표본·통계 근거가 부족. 미지원 후보 파일을 실제 성공 파일로 제공했다면 단순 미평가가 아니라 제공 경계 실패로 기록.

초기 hard gate는 확인된 신규 중대 결함 0건, stale/타인 파일 제공 0건, exact fallback 계약 100%다. 관측 0건이 모든 입력의 결함 0%를 보장하지는 않으며 표본 수·실패 수·불확실성을 함께 보고한다. 기준 파일 자체의 절대 결함도 별도로 차단하므로 ‘새로 악화되지 않았다’만으로 안전 인증하지 않는다.

품질 최소 개선폭·허용 회귀·필요 평가자/독립 묶음 수·최악 slice·지연 목표는 결과를 열기 전에 봉인한다. 기존 `refine_promotion_criteria.example.json`의 350개/12묶음/2초는 과거 **예시 값**이며 새 제품 계약에 무조건 적용하지 않는다. D1 분산과 묶음 구조로 필요한 표본을 정하고, 작가/작품 묶음을 고려한 paired 추정·신뢰구간을 사용한다.

## 11. 구현 순서와 완료 기준

| 순서 | 작업·담당 경계 | 완료 기준 |
|---|---|---|
| 1 | 데이터·공통 평가: 추론/평가 담당 + 도원 | selected12 GT 작성, 새 D1/D2 분리, rubric·정책 봉인, immutable manifest와 실패 행 검증 |
| 2 | 검색·리파인: 추론 담당 | 기존 runner 재사용, arm registry와 v3 evidence adapter, 고정 base 비교, 가림/귀속·복구 회귀, 원인별 report |
| 3 | 최종 파일: Converter 담당 + 도원 협업 | 실제 체형·손·범위별 메시/재import adapter, hash lineage, scene 변환·교차 검증, 양성·음성 fixture 통과 |
| 4 | 저장 경계: BFF·클라 담당 도원 | 기존 앱 계약을 사용하는 시나리오 runner, preview 지연·설정 변경·취소·stale·네이티브 저장 검증. 새로운 사용자 버튼은 불필요 |
| 5 | 활용성·승격: 작업자 + 평가 담당 | 블라인드 평가와 실제 수정 시간, 지원 범위별 coverage, 최악 slice·안전·시간 판정 보고서 |

새 모듈 후보는 `arms.py`, `artifact_lineage.py`, `export_runner.py`, `final_fbx_evaluator.py`, `mesh_evidence_adapter.py`, `save_scenarios.py`다. 이름은 제안이며 기존 데이터셋/라벨/보고서를 새로 만드는 중복 구현을 피한다. 오프라인 평가 기능은 제품 API·플래그 변경과 분리한다.

빠른 CI는 계약·합성·결정성·알려진 실패·exact fallback과 small fixture를 실행한다. 실제 VLM 호출은 별도 예산이 있는 수동/예약 평가에서 수행한다. 실제 Blender·설치 앱·CSP 검증도 환경과 대상 범위를 명시한다. 문서·mock 테스트만으로 제품 전체 통과라고 보고하지 않는다.

## 12. 첫 실행 결과물의 모습

평가 report 한 장에서 다음을 함께 확인할 수 있어야 한다.

1. 기준/후보 코드·자산·정책과 평가 범위, 전체/평가 완료/실패/unknown 수.
2. 원본 러프 → 인물/관절 overlay → Top-5 → 같은 선택 포즈의 전후 → 최종 파일 화면.
3. 검색 활용 가능률, 작가 선호·수정 시간, 실제 메시 안전, 저장 성공, 단계별 시간.
4. 좋아진 사례와 나빠진 사례, 가림/방향/다인/체형/손/출력 범위별 결과.
5. 결함의 관측 단계·근거·artifact ID·재현 방법. 원인 미확정은 미확정으로 표시.
6. `PASS / FAIL / INCONCLUSIVE`와 아직 검증하지 못한 profile·범위·도구·조합.

운영 대시보드는 실제 사용자가 어디에서 멈췄는지 보여주고, 이 하네스는 같은 입력에서 변경의 품질 효과를 비교한다. 연결은 코드/asset/app build·익명 case ID 수준으로 하고, 하네스의 정해진 과제 성공률을 실제 사용자 리텐션으로 표시하지 않는다.
