# 기본 체형 재사용과 포즈별 준비 시간 차이 검증

## 결론

운영에서 약 34.2초와 72.1초가 걸렸던 두 요청은 모두 `male-base-v0-8-0`,
명시적 체형 조절 없음이었다. 동일 포즈·자산으로 분리 실행하니 **두 포즈 모두
준비된 중립 체형을 실제 재사용**했다(`status=prepared`, `hit=true`).

차이는 기존 Converter의 **발바닥 각도 후보 탐색과 후보별 실제 메시 검사**에서 재현됐다.
느린 포즈는 보정 후보 38개를 탐색하고 표면 지표를 40회 계산한다. 검사 후에는
추가 보정을 채택하지 않고 부모 변환 결과로 복구하지만, 이미 계산 비용이 발생한다.

이번 변경은 계측과 재현 도구다. 보정 정책·품질 게이트·산출 형상을 바꾸지 않았고,
PR 병합·스테이징/운영 배포·운영 설정 변경은 수행하지 않는다.

## 재현 입력과 범위

- 운영 Converter 기준 커밋: `b56a92502567f9c2fdb5886f5fd09de6cab839cb`.
- 작업 기준: develop `2bb4ecbd4`. Converter 코드가 운영 기준과 동일함을 확인했다.
- 운영 Linux/amd64 이미지 digest: `sha256:a4d731fe35682f3e97f2bbeb53e188c3f43fd2bdc3f6da6a89cedb41ab2c5fd6`.
- Blender 5.2.0, build `fbe6228777e7`.
- 남성 모델: `male-base-v0-8-0`, SHA256 `705035f1bd247b3bf63a6d293065a5a39390b2d228df559474f9dc6682bf8c43`.
- 준비 자산: 운영 `prepared-all20-production-20261113-v1`의 남성 기본형.
- 현재 운영 라이브러리 `lib-20261112-f5c4b224`에서 두 BVH를 읽어 재현 입력과 바이트 일치를 확인했다.
- A: `g1__M_Move9__n05_f0810`, BVH `cc2c67e90e4cbe33f6a4833823189067939808b27c5e11afc2fe9ca43a276ce3`.
- B: `sd_cmu_124_01_f00424`, BVH `9265eed7d9c422ecc8d3ac2afc92d0f2d0d7b23ab2244628c5d6e3d03fb772b0`.
- 원본 손·기본 스킨·외곽선 없음·전신·체형 수치 변경 없음.
- 원본 BVH로 시작하고, VLM·검색·리파인은 재호출하지 않았다.
- 카메라는 고정 정면이다. 운영 검색 카메라를 재현한 것은 아니며,
  `body_prepare`는 원래 카메라 적용 전이므로 이번 병목 비교에는 영향을 주지 않는다.

로컬 Apple ARM Docker/Rosetta에서 **2 CPU / 4 GiB**, 네트워크 차단,
읽기 전용 코드·자산을 사용했다. 실제 Uvicorn HTTP → Blender prepare → solve →
FBX export → 별도 프로세스 재임포트 검증 → HTTP 파일 다운로드·저장까지 실행했다.
AWS 운영 하드웨어의 초 단위 절대 시간을 그대로 재현하는 실험은 아니다.

## 결과

기본 계측으로 A→B→B→A 순서, 상세 계측으로 A→B 순서로 실행했다.
각 실행마다 새 소유 범위를 사용해 포즈 적용 결과 캐시를 비운 조건으로 시작하고,
직후 같은 범위의 새 revision으로 재요청했다. 중립 체형 재사용은 모든 최초 요청에서 켰다.

| 항목 | A | B |
|---|---:|---:|
| 운영에 남은 `body_prepare` 시간 | 34.194초 | 72.075초 |
| 로컬 최초 준비 시간 범위, 각 3회 | 26.184~29.539초 | 70.209~74.416초 |
| 준비된 중립 체형 재사용 | 3/3 성공 | 3/3 성공 |
| 로컬 HTTP 요청→검증된 파일 저장 | 48.104~50.793초 | 90.845~96.709초 |
| 같은 결과 재요청→파일 응답 | 0.834~1.324초 | 0.897~1.278초 |

상세 계측 실행의 변환 내부:

| 단계 | A | B |
|---|---:|---:|
| 포즈 변환 전체 `retarget_convert` | 8.091초 | 53.917초 |
| 그 안의 발바닥 보정 `foot_plant` | 2.706초 | 49.515초 |
| 추가 보정 후보 수 | 0 | 38 |
| 발목 표면 지표 계산 | 2회 · 2.144초 | 40회 · 34.148초 |
| 발바닥 표면 지표 계산 | 2회 · 0.614초 | 40회 · 10.722초 |
| 정점 가중치 읽기 | 8회 · 1.939초 | 84회 · 16.997초 |
| 추가 발바닥 보정 채택 | 부모 결과 유지 | 부모 결과 유지 |

표의 단계는 **중첩 관계**이며 전부 합산하면 안 된다. 특히 정점 가중치 읽기는
표면 지표 계산 시간에 포함된다. `span_id`·`parent_span_id`로 포함 관계를 확인할 수 있다.
준비 체형 읽기는 두 포즈 모두 1초 미만이었다. 약 45.8초의 변환 시간 차이 대부분이
발바닥 후보 탐색에서 발생해 운영의 느린 포즈 분기를 재현했다.
과거 두 요청의 누락된 세부 로그를 소급 복원한 것은 아니므로 과거 37.9초 차이의
모든 밀리초를 단정하지 않는다.

## 로그 계약

- `converter_body_reuse`: `prepared/disabled/custom_shape/not_prepared/invalid_prepared`와 `hit`.
- `interactive_body_cache`: 포즈까지 적용한 private body base 캐시 적중 여부.
  중립 체형 재사용과 별개다. 이번 재요청 6건은 모두 이 캐시를 사용했다.
- `converter_body_stage`: 고정 단계명, span/parent ID, 시작 오프셋, 시간, 성공 여부.
- `converter_body_solver`: 고정 보정 단계명, 후보 개수, 부모 결과 복구 여부.
- API 부모 프로세스가 검증된 child 이벤트에 실제 `request_id`를 붙여 전달한다.
  stdout의 토큰·경로·형상·오류 원문·조작된 request ID는 전달하지 않는다.
- `CONVERTER_BODY_TRACE_ENABLED=0`으로 child 계측만 끌 수 있다.

준비 자산 identity를 구성하는 `prepared_body.py`, `shape_bake.py`, `shape_spec.py`,
`retarget.py`, `bone_map.py`, `final_artifact.py`는 바이트 그대로 유지했다.
별도 모듈의 delegate로 계측하고, 새 모듈은 interactive runtime identity에 포함했다.
따라서 계측 추가만으로 기존 중립 체형을 무효화하지 않는다.

## 검증과 후속 최적화 후보

- 관련 단위·계약 테스트 153개, 스모크 54개, Python compile, diff 공백 검사 통과.
- 최초 실행 6/6에서 최종 FBX 검증·다운로드·저장 통과. 재요청 6/6 HTTP 파일 응답 성공.
- 각 포즈의 모델 SHA256은 세 번의 실행과 계측 세분화 전후에 동일했다.
- 상세 숫자·영수증 요약은 같은 이름의 JSON에 보관한다.

속도를 줄이려면 발바닥 후보 탐색에서 같은 메시의 불변 가중치·정점 분류·위상 정보를
매번 읽는 부분을 우선 검토할 수 있다. 후보마다 달라지는 변형 좌표·안전 지표는 계속
검증해야 한다. 이 PR은 최적화나 검사 해제를 수행하지 않는다.

재현 도구는 `scripts/replay_body_prepare_trace.py --assets /app/body-staging --out /traceout/run --rounds 2`.
준비 자산과 원본 BVH를 해당 위치에 읽기 전용으로 마운트한 pinned Linux 이미지에서 사용한다.
